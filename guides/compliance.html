Module: Compliance & Governance Difficulty: Advanced Prerequisites: Financial module configured with tax settings, audit trail enabled

Overview

The Compliance & Governance module covers the full regulatory compliance landscape — VAT return preparation with SARS eFiling integration, immutable audit trail management, role-based access control governance with SOD conflict detection, POPIA compliance programme administration including DSAR workflows, document lifecycle management with retention schedules, compliance calendar with deadline escalation, tax reconciliations, external audit preparation, and regulatory change management.

Prepare and Submit VAT Returns

1
Reconcile VAT control account

Navigate to Compliance → VAT Returns → Reconciliation. The system compares the GL VAT control account balance to the VAT return calculated amount. Any difference must be investigated before submission. Common causes: missing tax invoices, incorrect VAT codes on transactions, or manual journal entries posted without VAT. The reconciliation report shows the difference amount and the contributing transactions. Resolve all differences before proceeding to submission.

2
Verify input VAT against AP

The system aggregates input VAT from all purchase transactions in the period. Verify that every supplier tax invoice has been captured with the correct VAT amount and VAT type (15% standard, 0% zero-rated, or exempt). Flag any invoices from non-vendors or missing tax invoices. The input VAT verification report lists all AP invoices with their VAT codes — review and correct any misclassified entries (e.g., zero-rated coded as standard).

3
Verify output VAT against AR

Output VAT is calculated from sales invoices, credit notes, and cash receipts. Review the output VAT breakdown by VAT type: standard-rated sales, zero-rated exports, exempt supplies (e.g., financial services), and deemed supplies (e.g., private use of business assets). The output VAT reconciliation report compares the AR VAT total to the GL output VAT account. Discrepancies may indicate invoices posted directly to GL without going through AR.

4
Handle zero-rated and exempt supplies

Zero-rated supplies (exports, certain food items) and exempt supplies (financial services, rental housing) must be reported separately on the VAT201 return. The system categorises these based on the item or service VAT code. Review the zero-rated and exempt schedules — ensure supporting documentation (e.g., export shipping documents, proof of delivery) is attached for zero-rated claims. SARS can request this documentation in an audit.

5
Generate VAT201 and submit via eFiling

Once the return is verified, click Generate VAT201. The system creates the XML file in the SARS eFiling format. Download the file and upload to SARS eFiling, or use the integrated eFiling API if configured. Enter the SARS received reference number in the system to close the VAT period. Track the VAT payment due date — if the return shows VAT payable, schedule the payment to arrive at SARS before the 25th of the month to avoid 10% penalties.

Configure and Review Audit Trails

1
Configure audit event categories

Navigate to Settings → Audit Trail → Configuration. Enable event categories: Create, Update, Delete, Login, Logout, Export, Print, and Permission Change. For each module, select which events to capture — financial modules should capture all events, while reference data modules may only need Create and Delete. Capturing every event generates large volumes of data, so balance audit requirements against storage capacity. Configure minimum 12 months retention for general events and 5 years for financial events.

2
Set audit log retention period

In Settings → Audit Trail → Retention, set retention periods per event category. Financial audit events: 5 years (SARS requirement). User access events: 2 years. System configuration changes: permanently. The system auto-archives events older than the retention period to compressed storage. Archived events are still searchable but may have slower retrieval. Ensure sufficient storage is allocated before going live — a busy ERP can generate 50 000+ audit events per month.

3
Search and filter audit trail

The Audit Trail Viewer supports complex filtering: by module (Procurement, Financials, Stock), by user, by date range, by event type (Create, Delete), and by record ID. Use the Advanced Search to find specific transactions — for example, find all changes to supplier bank accounts in the last 30 days. Search results show: timestamp, user, IP address, module, record ID, action, and before/after values. Export results to CSV for further analysis.

4
Review before/after value comparison

Each audit entry captures the previous and new values for changed fields. For a supplier bank account change, the audit entry shows: Field = Bank Account, Before = 1234567890, After = 0987654321, Changed By = John Smith, Timestamp = 2026-06-15 14:30:22, IP = 192.168.1.50. Use the comparison view to spot suspicious activity — if a supplier's bank account was changed and a payment was processed the same day, this is a red flag for payment fraud.

5
Verify audit log integrity

Audit trail records are immutable — they cannot be edited or deleted by any user, including administrators. The system uses cryptographic hashing: each record contains a hash of the previous record, creating a chain. Run the Integrity Check from Settings → Audit Trail → Integrity to verify the hash chain has not been broken. If a break is detected, investigate immediately — it indicates the audit log has been tampered with at the database level.

Implement Role-Based Access Control Governance

1
Define RBAC policy and approval

Navigate to Settings → Security → RBAC Policy. Document the access control policy: who can request role changes, who authorises them, and the review frequency. For each role, document the business justification: Financial Manager requires access to GL, AP, AR, and Reporting; Warehouse Operator requires access to Stock, Picking, and GRN. The policy document is stored in the document repository and must be signed off by the compliance officer and IT manager.

2
Detect segregation of duties conflicts

Run the SOD Conflict Report from Settings → Security → SOD. The report checks for incompatible permission combinations across all users. Critical SOD rules: Create Supplier + Approve Invoice; Create PO + Approve PO; Post GL Journal + Approve GL Journal; Create User + Assign Roles. The report lists each conflict with the user, the conflicting permissions, and the risk level (High/Medium/Low). Resolve high-risk conflicts within 7 days by reassigning one of the permissions.

3
Run periodic access review

Schedule quarterly access reviews. The system generates an Access Review worksheet listing all users, their roles, and last login date. The review is assigned to each department manager — they verify that their team members still need the access they have. Mark users for removal (leavers), role changes (transfers), or retention. The compliance officer reviews the completed worksheet and implements changes. Overdue access reviews are escalated to the steering committee.

4
Manage temporary access provisioning

For temporary access (contractors, interns, auditors), use the Temporary Access function. Set an expiry date — access is automatically revoked on that date. Example: external auditor needs read-only access to GL and AP for 2 weeks. Create a temporary Auditor role, assign it to the user, set expiry to 14 days. The system sends a reminder 2 days before expiry and revokes access automatically on the expiry date. The temporary access log records all such provisions for audit.

5
Run RBAC audit report

The RBAC Audit Report shows: all users with their roles and permissions, SOD conflicts (current and resolved), access review completion status, temporary access provisions, and permission change history. This report is used by external auditors to verify access control effectiveness. Export the report at each audit period end and store it in the compliance document repository with the audit sign-off.

Manage POPIA Compliance Programme

1
Create personal data inventory (ROPA)

Navigate to Compliance → POPIA → ROPA (Record of Processing Activities). Document each data processing activity: data category (customer personal data, employee data, supplier contact data), purpose (processing orders, payroll, supplier management), lawful basis (consent, contractual necessity, legal obligation), data subjects, data retention period, and data recipients (third parties, SARS, DOL). The ROPA must be reviewed annually and updated within 30 days of any new processing activity.

2
Document lawful basis for processing

For each processing activity, record the lawful basis: Consent (marketing emails, customer surveys), Contractual Necessity (order processing, delivery), Legal Obligation (tax reporting, payroll deductions), Legitimate Interest (fraud prevention, credit checks), or Public Task. Consent records must include: date obtained, method (web form, signed form, verbal), consent text, and withdrawal date if applicable. The consent register is searchable by data subject.

3
Manage consent with withdrawal tracking

The consent management dashboard shows: total consents, consents by purpose, withdrawal rate, and pending withdrawal requests. When a data subject withdraws consent, the system records the withdrawal date and time, and flags the record for processing restriction. Marketing preferences are updated immediately to stop further communications. Withdrawal does not affect processing that was done before the withdrawal or processing based on a different lawful basis (e.g., legal obligation).

4
Process data subject access requests

When a DSAR is received, log it in Compliance → POPIA → DSAR. The system compiles all personal data for that data subject across all modules: customer record, contact details, transaction history, communication log, consent records, and support tickets. Package the data as a structured export (Excel or PDF) within 30 days (POPIA requirement). The DSAR workflow tracks: receipt date, response due date, data compilation status, review and approval, and dispatch confirmation. Late responses are flagged for management escalation.

5
Prepare for data breach notification

If a data breach is suspected, use the Breach Notification workflow in Compliance → POPIA → Breach. Document the breach details: discovery date and time, data categories affected, number of data subjects, potential impact, and containment actions. The Information Regulator must be notified within 72 hours of becoming aware of the breach. The system generates the notification form and tracks the submission. Affected data subjects must also be notified if the breach poses a risk to their rights and freedoms.

Configure Compliance Calendar

1
Define regulatory deadlines

Navigate to Compliance → Calendar → Deadline Types. Configure recurring deadlines: VAT Returns — 25th of month following period end; PAYE — 7th of following month; Annual Returns — within 30 days of financial year end; POPIA Report — annual by 30 June; BEE Certificate Renewal — annual; WCA Returns — annual by 31 March. Each deadline has a regulatory reference, penalty for late submission, and responsible role. The calendar auto-populates for the next 12 months.

2
Set automated deadline alerts and escalation

Configure alert timing for each deadline type: Initial reminder 30 days before due date, Warning reminder 14 days before, Urgent reminder 7 days before, Overdue notification on the due date. Escalation: if the task is not marked complete by the due date, escalate to the manager on day 1, to the director on day 7, and to the compliance officer on day 14. Alerts are sent via email and in-app notification. Each escalation logs an audit trail entry.

3
Assign and track compliance tasks

Each deadline generates a compliance task assigned to the responsible person. Tasks have: description, due date, checklist of required actions, document upload requirement (e.g., proof of submission), and sign-off field. The task dashboard shows overdue, pending, and completed tasks for each user. The compliance manager runs the Compliance Task Status report weekly to identify overdue filings before penalties accrue.

4
Handle deadline extensions

If a filing deadline cannot be met, log an extension request in the calendar. SARS grants automatic extensions for certain returns (e.g., provisional tax). Record the extension reference number and new due date. The system recalculates the deadline alerts based on the extended date. Extensions must be approved by the compliance officer. The extension log shows all extensions granted and the reasons, providing an audit trail for late filings.

5
Generate compliance calendar report

The Compliance Calendar Report shows all deadlines for a selected period (monthly, quarterly, annually). Columns: Deadline Type, Due Date, Status (Complete/Pending/Overdue), Responsible Person, Days Overdue (if applicable). Filter by status to focus on overdue items. Export to PDF for board reporting or Excel for detailed tracking. The annual compliance calendar is reviewed and approved by the board at the start of each financial year.

Set Up Document Lifecycle Management

1
Create document classification and metadata schema

Navigate to Compliance → Documents → Classification. Define document categories: Tax Documents (VAT returns, tax certificates, EMP201), Contracts (supplier contracts, customer contracts, lease agreements), HR Records (employment contracts, disciplinary records, medical certificates), Policies (POPIA policy, IT security policy, HR policy), and Audit Reports (internal audit, external audit, regulatory audit). Each category has mandatory metadata: document type, date, expiry date, responsible person, and retention period.

2
Set retention schedule by document category

Configure retention periods per category: Tax documents — 5 years from year of assessment (SARS requirement). Contracts — 3 years post-termination (contract law). Employment records — 3 years post-employment (BCEA), 5 years for medical records (OHSA). Financial records — 5 years (Companies Act). Once the retention period expires, the document is flagged for review. If no legal hold applies, it moves to Archive status for 12 months, then automatically deleted.

3
Automate archival and secure deletion

Documents reaching their retention end date are moved to the Archive. Archived documents are compressed and moved to long-term storage (slower retrieval but lower cost). After the archive period expires, the system schedules secure deletion — files are overwritten and the metadata is purged. The deletion log records: document ID, category, deletion date, and authorising user. If a deletion is blocked (e.g., litigation hold), the document remains in Archive status with a hold flag.

4
Manage document version control with approval

When a document is updated, the new version is uploaded and the system increments the version number (v1, v2, v3). The version history shows each version with upload date, uploader, and change notes. For policy documents, enable the approval workflow — the updated version must be reviewed and approved before it replaces the current version. Previous versions are retained for audit reference. The Document Version Report shows the version history for all documents in a category.

5
Manage litigation hold overrides

When litigation is anticipated or in progress, all relevant documents must be preserved regardless of retention schedule. Use the Litigation Hold function: select the documents or categories, enter the legal case reference, and set the hold expiry date (when litigation concludes). Documents under hold are excluded from archival and deletion processes. The hold register is reviewed monthly by the legal team. When the hold is released, documents resume their normal retention lifecycle.

Run Tax Reconciliations

1
Reconcile VAT return to GL VAT account

Navigate to Compliance → Tax Reconciliations → VAT. The reconciliation compares the VAT return output (from AR/AP) to the GL balance of the VAT control accounts. Formula: GL VAT Control Account Balance − VAT Return Amount = Variance. If variance > 0, investigate: missing invoices, incorrect VAT codes, unprocessed credit notes, or journal entries affecting VAT accounts. The reconciliation must be signed off by the financial manager before the VAT return is submitted.

2
Reconcile PAYE to EMP201

The PAYE reconciliation compares the GL payroll tax account to the EMP201 return. Components: PAYE on salaries, UIF, SDL, and Skills Development Levy. Differences arise from: payroll adjustments after the PAYE run, fringe benefit calculations, or manual adjustments. Run the reconciliation after each payroll run and before EMP201 submission. The reconciliation report shows each component's GL balance vs return amount, with drill-down to employee-level details.

3
Reconcile turnover to SARS declarations

Annual turnover declared to SARS (for income tax) must match the system's total revenue per the financial statements. The Turnover Reconciliation Report compares: system revenue (P&L total income) vs prior year SARS return vs estimated current year. Significant variances (over 10%) require explanation: changes in business model, acquisitions/divestments, or accounting policy changes. The reconciliation is reviewed by the external auditors during the annual audit.

4
Investigate and resolve discrepancies

When a discrepancy is found, create a discrepancy case from the reconciliation. Document the cause: system error (incorrect VAT code on an item), process error (invoice posted to wrong period), or data entry error (wrong amount captured). Assign the case to the responsible person for resolution. Track resolution status and timeliness. All discrepancies must be resolved before the relevant return is finalised. The discrepancy resolution log serves as internal audit evidence.

5
Sign off and archive reconciliation

Once the reconciliation is complete and variance is zero or explained, the financial manager and compliance officer sign off digitally. The signed-off reconciliation is stored in the document repository with the period reference. This documentation is critical for external audit — auditors will request reconciliations for the periods under review. Maintain a reconciliation sign-off register showing all periods completed, signed off, and available for audit.

Prepare for External Audit

1
Compile audit evidence from system

Navigate to Compliance → Audit Preparation → Evidence Compilation. Select the audit period and modules under review. The system generates an evidence package: audit trail export, user access list, RBAC configuration report, SOD conflict report, document retention compliance report, and key transaction reports (sales, purchases, payroll). Each evidence item is indexed and cross-referenced to the audit programme. The evidence package can be exported as a single PDF or ZIP of individual files.

2
Generate audit trail reports by module

For each module under audit, generate module-specific audit trail reports: Financials — all GL journal postings, AP payments, AR receipts; Procurement — PO changes, GRN postings, matching events; Stock — inventory adjustments, stock takes, transfers; HR — employee data changes, payroll runs. Filter by the audit period and order chronologically. Each report includes the user, timestamp, and before/after values. These reports form the primary evidence for transaction testing.

3
Package documents for auditor review

The Document Collection tool gathers all documents relevant to the audit: signed financial statements, board minutes, tax returns, contracts above materiality threshold, and policies. Organise by category and period. Create an audit document index with hyperlinks to each document. The auditor receives read-only access to the document repository through a secure portal. Grant access with an expiry date matching the audit engagement period.

4
Provision auditor access (read-only)

Create an External Auditor role with read-only access to the modules under audit. Permissions: view only — no create, edit, delete, or export without approval. Set a hard expiry date on the auditor user account. The auditor's activities are logged in the audit trail — if they export data, the event is recorded. Review the auditor activity log weekly during the audit engagement to ensure access is being used appropriately.

5
Track audit findings and remediation

When the auditor issues findings, log them in Compliance → Audit → Findings. Each finding has: description, risk rating, remediation action, responsible person, target date, and status. Track remediation progress through the Findings Dashboard — overdue items are escalated. When remediation is complete, the system notifies the auditor for verification. The audit findings history is maintained for the next audit cycle to demonstrate continuous improvement.

Maintain Regulatory Change Management

1
Create regulations register and applicability matrix

Navigate to Compliance → Regulatory Change → Register. Document all applicable regulations: VAT Act, Income Tax Act, POPIA, BCEA, OHSA, BEE Act, Companies Act, and industry-specific regulations. For each regulation, record the issuing body, last amendment date, next review date, and applicability to your business (applies fully, partially, or not applicable). The applicability matrix maps each regulation to the affected module and processes. Review annually and update within 30 days of a regulatory change.

2
Monitor regulatory updates

Subscribe to regulatory update feeds in the system — SARS announcements, Government Gazette changes, and industry body notifications. When a regulatory update is received, log it in the system with the effective date and summary of changes. Assess the impact: does this affect system configuration, processes, or reporting? The regulatory update log shows all changes, their assessed impact, and implementation status. This log is reviewed in quarterly compliance committee meetings.

3
Assess impact on system configuration

When a regulation changes, perform an impact assessment: Does the VAT rate change require updating tax codes? Does a new reporting requirement need a new report? Does a change in data retention periods require updating the retention schedule? Document the assessment in the system, assign implementation tasks to the relevant team members, and set target dates. High-impact changes (e.g., VAT rate change) are escalated to the project steering committee.

4
Track compliance requirement implementation

Each regulatory change generates implementation tasks: configuration changes, process updates, report development, and staff training. The implementation dashboard shows status by regulation: Not Started, In Progress, Testing, Completed, and Verified. Changes must be tested in the sandbox environment before production deployment. A change management log records all system changes made for regulatory compliance, with audit trail evidence of testing and sign-off.

5
Deliver regulatory change training and communication

When a regulatory change is implemented, create training materials and communications for affected staff. The system tracks training completion: who has been trained, who has acknowledged the policy change, and who still needs training. Overdue training assignments are escalated to department heads. The training record is maintained for auditor review — auditors will check that staff were trained on regulatory changes within a reasonable timeframe of implementation.

Warning

VAT returns must be submitted within 25 days of the period end. Late submissions attract penalties of 10% of the VAT due plus interest at the prescribed rate per month.

Info

POPIA requires that data subjects can request access to their personal data within 30 days. The DSAR workflow tracks response timelines automatically and escalates overdue requests.

Tip

Run the SOD conflict report quarterly to identify users with incompatible permissions (e.g., creating suppliers and approving invoices). High-risk conflicts should be resolved within 7 days.

Warning

Audit trail records are immutable — they cannot be edited or deleted. Configure sufficient storage for your retention period before going live. Running out of audit log storage can halt system operations.

Info

Document retention schedules must comply with specific legislation: tax records 5 years (SARS), employment records 3 years (BCEA), medical records 6 years (OHSA). Configure these in the document lifecycle settings.
